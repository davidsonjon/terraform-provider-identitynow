# identitynow_source_v1 (Resource)

Manages a [Source](https://documentation.sailpoint.com/saas/help/sources/index.html) in IdentityNow/ISC.

~> This is a `_v1` pilot resource - see the "Known Limitations & Live Testing Notes" section below before relying on it in production configurations. Only core create/read/update/delete lifecycle attributes are modeled here - provisioning policies, schemas, schedules, connections, source health, correlation config, password policies, connector test/discovery operations, and several other sub-resource endpoints are deliberately deferred (see the package doc).

## Example Usage

```terraform
resource "identitynow_source_v1" "example" {
  name      = "example-source"
  connector = "delimited-file"

  description = "Managed by Terraform."

  owner = {
    id   = "2c91808576ddc7060176de5040574aa0"
    type = "IDENTITY"
  }

  # "connector_attributes" is connector-type-specific raw JSON - see this
  # resource's "Known Limitations & Live Testing Notes" documentation section
  # for why it's modeled as a JSON string rather than a fixed schema.
  connector_attributes = jsonencode({
    fileLocationType = "S3"
  })

  # Optional attributes below - all confirmed against a real Delimited File
  # source in a live sandbox tenant unless noted otherwise.

  # "cluster" is intentionally omitted here: it only applies to
  # "direct"-connection sources (e.g. Active Directory, SCIM, JDBC) - a
  # "file"-connection source like this Delimited File example always has
  # `cluster = null` regardless of configuration (confirmed live).

  # "account_correlation_config" cannot be set to reference an arbitrary
  # existing correlation config: live testing confirmed each config is
  # generated per-source (its own display name embeds the owning source's
  # id, e.g. "Directory [source-62867] Account Correlation" per the spec's
  # own example) and the API returns "HTTP 404, ... target resource" if you
  # try to create a new source referencing another source's correlation
  # config id. Left unset here; if you have a verified valid id scoped to
  # this exact source (e.g. captured via import after an out-of-band
  # change), it can be set the same shape as shown in the commented
  # "account_correlation_rule" alternative below.
  # account_correlation_config = {
  #   id   = "<a correlation config id scoped to this specific source>"
  #   type = "ACCOUNT_CORRELATION_CONFIG"
  # }

  # "account_correlation_rule" is a mutually exclusive alternative to
  # "account_correlation_config" above - only use one or the other. Shown
  # here commented out for illustration; do not set both in a real config.
  # account_correlation_rule = {
  #   id   = "2c9180835d2e5168015d32f8ce440e88"
  #   type = "RULE"
  # }

  # "management_workgroup" references a governance group - if it's managed
  # by Terraform too, this provider's own identitynow_governance_group_v1
  # resource can supply its id, e.g.:
  #   management_workgroup = {
  #     id   = identitynow_governance_group_v1.example.id
  #     type = "GOVERNANCE_GROUP"
  #   }
  management_workgroup = {
    id   = "74fd5c69-f542-48fe-8909-60ae705adce4"
    type = "GOVERNANCE_GROUP"
  }

  # Optional features supported by this connector - modifying this is only
  # recommended for connectors that document specific feature support.
  features = [
    "DIRECT_PERMISSIONS",
    "DISCOVER_SCHEMA",
  ]

  delete_threshold            = 10
  credential_provider_enabled = false
  # "category" is intentionally omitted - it's Computed-only. Live testing
  # confirmed the API silently ignores any configured value (every source in
  # this tenant returns category = null regardless of connector type), so
  # Terraform can only read it, never set it.
}
```

## Known Limitations & Live Testing Notes

This resource is a `_v1` pilot: schema/model types are generated by
`tfplugingen-framework` from SailPoint's per-service `/sources/v1` OpenAPI
spec (service folder `sources`), but Create/Read/Update/Delete are
hand-written against the `golang-sdk`'s `api_beta.SourcesAPIService` client.

- **Scope is intentionally limited to core Source CRUD.** This resource only
  covers `POST /sources/v1`, `GET /sources/v1/{id}`, `PATCH /sources/v1/{id}`
  (JSON Patch), and `DELETE /sources/v1/{id}`. The following related
  sub-resource/action endpoints are all explicitly **out of scope** and
  unaffected by this resource: provisioning policies, schemas, schedules,
  connections, source health, correlation config, password policies,
  native change detection config, connector actions (check-connection,
  peek-resource-objects, ping-cluster, test-configuration,
  upload-connector-file, connectors/source-config), account
  load/remove/synchronize actions (remove-accounts, load-accounts,
  load-uncorrelated-accounts, synchronize-attributes, load-entitlements),
  attribute sync config, entitlement request config, and approval config.
  Managing any of these requires a future, separate resource/data source.
- **Only `PATCH /sources/v1/{id}` (JSON Patch) is used for updates** - the
  full-replace `PUT /sources/v1/{id}` variant is not used. Per the API's own
  documentation, `id`, `type`, `authoritative`, `created`, `modified`,
  `connector`, `connectorClass`, and `passwordPolicies` are immutable and
  cannot be patched after creation.
- **`connector_attributes` is a raw JSON string (`jsontypes.Normalized`), not
  a fixed schema.** Its real shape is entirely connector-type-dependent (a
  Delimited File source's attributes look nothing like a Workday or Active
  Directory source's) - see this repository's `transform_v1` resource for
  the same modeling pattern applied to a different dynamic/discriminated-union
  field. The live API always merges its own server-computed status keys
  (`healthy`, `since`, `status`, `connectionType`, `connectorName` -
  duplicates of the top-level attributes of the same purpose) into this same
  JSON object on every response, so this resource always preserves your
  configured value as the source of truth in state rather than round-tripping
  the API's enriched superset back (which would otherwise cause a permanent
  "inconsistent result" apply error) - only an unconfigured/imported source
  gets its `connector_attributes` populated from the live API response.
- **`schemas` and `password_policies` are Computed-only, read-back
  reflections of state managed elsewhere** (the deferred sub-resource
  endpoints listed above) - they are never written by this resource's
  Create/Update and will not drift-correct if changed out of band.
- **`cluster` is populated via a hand-written conversion, not a generated
  type-mapped converter.** The SDK's `MultiHostIntegrationsCluster` struct
  has non-pointer, always-required `Id`/`Name`/`Type` fields (unlike every
  other mapped nested object here), which is incompatible with
  `tfplugingen-framework`'s generated converter template - see
  `generator_config/type_mappings_sources_v1.yml`'s header comment for the
  full rationale. **`cluster` only applies to "direct"-connection sources**
  (`connection_type = "direct"`, e.g. Active Directory, SCIM, JDBC, web
  services connectors) - confirmed live against a real tenant that every
  "file"-connection source (`connection_type = "file"`, e.g. Delimited File)
  has `cluster` unset/null regardless of configuration; leave it unset for a
  file-based source.
- **`account_correlation_config` and `account_correlation_rule` are mutually
  exclusive alternatives, per the API's own documentation**: "Only use
  [`account_correlation_rule`] when you can't use
  [`account_correlation_config`]." Similarly, **`manager_correlation_mapping`
  and `manager_correlation_rule` are mutually exclusive alternatives**: "Only
  use [`manager_correlation_rule`] when a simple filter isn't sufficient."
  This provider does not currently enforce either mutual exclusivity with a
  validator - setting both members of a pair is accepted by the schema but
  its effective behavior is entirely up to the live API.
- **`account_correlation_config` cannot reference an arbitrary existing
  correlation config from another source - confirmed live.** Each config
  appears to be generated per-source (the spec's own example display name is
  `"Directory [source-62867] Account Correlation"`, embedding the owning
  source's id), and attempting to `Create` a *new* source with
  `account_correlation_config.id` set to a real correlation config id
  belonging to a *different*, pre-existing source fails with `HTTP 404, ...
  The server did not find a current representation for the target
  resource.` (reproduced consistently, is not transient). This attribute's
  own CRUD is a separate, out-of-scope endpoint
  (`/sources/v1/{sourceId}/correlation-config`, deferred - see above); until
  that's implemented, leave `account_correlation_config` unset unless you
  have a verified valid id scoped to this exact source (e.g. captured via
  `terraform import` after an out-of-band change). The same
  out-of-scope-reference caveat applies to any rule reference
  (`account_correlation_rule`, `manager_correlation_rule`,
  `before_provisioning_rule`), which reference SailPoint Cloud Rules managed
  entirely outside this provider's current scope - those were not observed
  to fail the same way live, but weren't exercised with a real rule id
  either.
- **`management_workgroup` references a governance group** (`type =
  "GOVERNANCE_GROUP"`) - confirmed live against a real tenant, including a
  full create -> no-drift-replan -> update -> destroy cycle. If the
  referenced group is managed by Terraform too, this repository's
  `identitynow_governance_group_v1` resource can supply that id (e.g.
  `management_workgroup = { id = identitynow_governance_group_v1.example.id,
  type = "GOVERNANCE_GROUP" }`), giving a real cross-resource composition
  example within this provider.
- **`Update` only patches `connector_attributes` when it actually changed
  vs. the last-read state - not unconditionally on every update.** Live
  testing uncovered a real bug: since the API injects extra,
  connector-specific computed keys into this object on `Read` (see the
  `connector_attributes` bullet above), re-sending only the practitioner's
  minimal configured subset on *every* `Update` - even when unrelated
  attributes changed and `connector_attributes` itself did not - caused the
  API to reject the request with a confusing, unrelated `HTTP 400, Illegal
  attempt to modify "healthy" field` error (`healthy` was never itself in
  the patch; this appears to be the server's generic immutable-field diff
  check misfiring when `connectorAttributes` changes shape relative to its
  live-only computed keys). Fixed by only including the
  `/connectorAttributes` patch op when `connector_attributes` genuinely
  changed. A real, intentional change to `connector_attributes` may still hit
  this same API-side quirk - tracked as a known limitation, not fully fixed.
- **The `provisionAsCsv` create-time query parameter is not yet exposed as a
  resource attribute.** Per the API's own documentation: "If you don't set
  this query parameter and you attempt to set the `type` attribute directly,
  the request won't correctly generate the source" when creating a Delimited
  File source. This resource currently always creates without that query
  parameter set, which is only safe as long as you leave `type` unset
  (Computed) and let the connector value alone determine the resulting
  source type - confirmed live (a Delimited File source created this way
  correctly comes back with `type = "Delimited File"`). Explicitly setting
  `type` yourself when creating a Delimited File source is unsupported until
  a future revision exposes `provisionAsCsv`; tracked as a follow-up.
- **`healthy` intentionally has no static schema default**, even though the
  OpenAPI spec declares `default: false` on it. It's a genuinely
  server-computed status field (whether the source's most recent health
  check passed) whose live value depends on server-side state - a static
  default previously caused a real "Provider produced inconsistent result
  after apply" error the moment the live value differed from the spec's
  stated default, fixed via
  `generator_config/schema_overrides_sources_v1.yml`'s `strip_defaults`
  entry. Leave it unconfigured and let the live value populate it.
- **`category` is Computed-only (not settable via Terraform config).** The
  OpenAPI spec generates it as `computed_optional`, but live testing proved
  the API silently ignores any value a practitioner configures: every
  existing real source in this tenant returns `category = null` regardless
  of connector type, and an apply that explicitly set
  `category = "CredentialProvider"` on create still came back `null` from
  the API - a permanent (not just first-apply) "Provider produced
  inconsistent result after apply" error as long as the attribute stayed
  Optional. Forced Computed-only via
  `generator_config/schema_overrides_sources_v1.yml`'s
  `computed_only_overrides` entry, so Terraform can only read this
  attribute's server-reported value, never configure it.
- **Live sandbox-tenant verification (Phase B) is complete for this pilot.**
  A full create -> read -> no-drift-replan -> destroy cycle has been run
  against a real tenant, including the fixes above.
