# identitynow_source_schema_v1 (Resource)

Manages a [Schema](https://documentation.sailpoint.com/saas/help/accounts/schema.html) (account or group/entitlement attribute definitions) on an existing [Source](https://documentation.sailpoint.com/saas/help/sources/index.html) in IdentityNow/ISC.

~> This is a `_v1` pilot resource - see "Known Limitations & Live Testing Notes" below before relying on it in production configurations.

## Example Usage

```terraform
# A Schema defines the attributes IdentityNow aggregates for a given
# object type (account or, for group/hierarchical sources, entitlement) on
# a source. Composite id = source_id + schema_id (this resource's own "id"
# and "schema_id" outputs are always equal - see "Known Limitations & Live
# Testing Notes").
resource "identitynow_source_schema_v1" "example" {
  source_id          = "9e99be10dcf24aa9bbe83902dece8738"
  name               = "account"
  native_object_type = "User"
  identity_attribute = "sAMAccountName"
  display_attribute  = "sAMAccountName"

  attributes = [
    {
      name           = "sAMAccountName"
      native_name    = "sAMAccountName"
      type           = "STRING"
      description    = "Account ID"
      is_multi       = false
      is_entitlement = false
      is_group       = false
    },
    {
      name           = "memberOf"
      native_name    = "memberOf"
      type           = "STRING"
      description    = "Group membership"
      is_multi       = true
      is_entitlement = true
      is_group       = true
      schema = {
        id   = "2c91808a7813090a017814121919ffff"
        name = "group"
        type = "CONNECTOR_SCHEMA"
      }
    },
  ]

  # "configuration" is a free-form JSON object with no fixed set of keys -
  # see this resource's "Known Limitations & Live Testing Notes"
  # documentation section for the full rationale.
  configuration = jsonencode({})
}
```

## Known Limitations & Live Testing Notes

This resource is a `_v1` pilot. `identitynow_source_v1`'s own docs note
provisioning policies and schemas as sub-resources of a Source deferred to
"a future, separate resource/data source" - this is that resource for
Schemas (see `identitynow_source_provisioning_policy_v1` for Provisioning
Policies).

- **Only the JSON CRUD schema endpoints are covered.** The upstream
  `sources` service also exposes CSV-based account/entitlement schema
  template download/upload endpoints
  (`sources-v1-by-id-schemas-accounts.yaml` /
  `sources-v1-by-id-schemas-entitlements.yaml`, `text/csv` and
  `multipart/form-data` file transfers scoped to Delimited File sources
  only). These are intentionally out of scope: they are file-transfer
  operations, not structured JSON CRUD, and are a poor fit for a
  declarative Terraform resource/data source - `tfplugingen-openapi`/
  `-framework` also cannot generate anything meaningful from them.
- **`id` and `schema_id` are redundant, both server-generated Computed-only
  outputs.** `tfplugingen-openapi` generates both a real `id` (from the
  Schema DTO body) and a synthesized `schema_id` (from the `{schemaId}`
  path parameter) - the two are always equal in practice. Both are forced
  Computed-only via `schema_overrides_source_schema_v1.yml`, since neither
  is meaningfully settable by a practitioner (a new schema's real id is
  only known after `Create`). This resource's own Terraform `id` is the
  same composite shape used elsewhere in this provider,
  `<source_id>/<schema_id>`, for consistent `terraform import` behavior -
  not the raw Schema DTO id alone.
- **`name`, along with `created`/`modified`, is immutable after creation**
  per `putSourceSchemaV1`'s own documented "cannot be updated" field list
  (attempting to change it returns a `400`). `name` therefore forces
  replacement here (`created`/`modified` are Computed-only outputs, so
  they can't be configured in the first place).
- **`configuration` is modeled as a raw JSON string**
  (`jsontypes.Normalized` - semantic, not textual, equality), since it's a
  free-form object bag with no fixed set of keys, the same "arbitrary JSON
  blob" shape as `identitynow_transform_v1`'s `attributes` and
  `identitynow_source_v1`'s `connector_attributes`. See those resources'
  own "Known Limitations" sections for the general rationale.
- **`attributes[].schema` refers to another Schema** (e.g. a group/
  entitlement schema referenced from an account schema's `memberOf`-style
  attribute) via `{id, name, type}` - it does not embed that schema's full
  definition, only a pointer to it.
- **Update uses `PATCH` (RFC 6902 JSON Patch)**, matching
  `identitynow_source_v1`/`identitynow_role_v1`/
  `identitynow_service_desk_integration_v1`/
  `identitynow_source_provisioning_policy_v1`'s existing JSON-Patch
  update-helper pattern, not the also-available full-replace `PUT` variant.
- **A plural `identitynow_source_schemas_v1` data source is fully
  hand-written**, not generated by `tfplugingen-framework` (which has no
  "list" operation concept) - it reuses this resource's own generated
  schema/model types, mirroring `identitynow_roles_v1`'s precedent.
- **Phase B (live `terraform plan`/`apply`/`destroy` against a real sandbox
  tenant) is complete for this pilot.** A full create/plan(no-drift)/destroy
  cycle was confirmed against a real tenant (`test/source_schema/main.tf`),
  with no drift or provider-inconsistency errors observed. The
  cross-schema-reference deletion-order question (whether deleting a schema
  still referenced by another schema's `attributes[].schema` pointer is
  rejected) was not exercised in this pass - the test fixture used a single
  standalone schema - so that edge case remains untested.
