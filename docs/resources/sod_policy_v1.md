# identitynow_sod_policy_v1 (Resource)

Manages a [Separation of Duties (SOD) Policy](https://documentation.sailpoint.com/saas/help/sod/manage-policies.html) in IdentityNow/ISC. SOD policies let administrators prevent identities from gaining conflicting or excessive access, either via a free-form search `policy_query` (`type = "GENERAL"`) or via two structured `conflicting_access_criteria` entitlement lists (`type = "CONFLICTING_ACCESS_BASED"`).

~> This is a `_v1` pilot resource - see the "Known Limitations & Live Testing Notes" section below before relying on it in production configurations. Note also that the read-only `identitynow_governance_group_connections_v1` data source surfaces a `SOD_POLICY` connection type for governance groups referenced as a policy/violation owner - see that data source's docs for the reverse-lookup relationship.

## Example Usage

```terraform
resource "identitynow_sod_policy_v1" "example" {
  name                     = "example-sod-policy"
  description              = "Managed by Terraform. Flags identities with conflicting finance access."
  external_policy_reference = "FIN-SOD-001"
  compensating_controls    = "Quarterly manager attestation review."
  correction_advice        = "Remove one of the conflicting entitlements or request a policy exception."
  state                    = "ENFORCED"
  scheduled                = false
  type                     = "CONFLICTING_ACCESS_BASED"
  tags                     = ["finance", "sox"]

  owner_ref = {
    type = "IDENTITY"
    id   = "2c9180835d191305015d28d181fc1234"
    name = "Support"
  }

  conflicting_access_criteria = {
    left_criteria = {
      name = "AP Invoice Approval"
      criteria_list = [
        {
          type = "ENTITLEMENT"
          id   = "2c9180846b0910c8016b0911d4a10101"
          name = "AP-Invoice-Approver"
        }
      ]
    }
    right_criteria = {
      name = "AP Payment Processing"
      criteria_list = [
        {
          type = "ENTITLEMENT"
          id   = "2c9180846b0910c8016b0911d4a10202"
          name = "AP-Payment-Processor"
        }
      ]
    }
  }

  violation_owner_assignment_config = {
    assignment_rule = "MANAGER"
  }
}
```

## Known Limitations & Live Testing Notes

This resource is a `_v1` pilot: most schema/model types are generated by
`tfplugingen-framework` from SailPoint's per-service `/sod-policies/v1`
OpenAPI spec (service folder `sod-policies`), but Create/Read/Update/Delete
are hand-written against the `golang-sdk`'s `api_beta.SODPoliciesAPI`
client.

- **`conflicting_access_criteria` and `violation_owner_assignment_config`
  are entirely hand-written, not generated.** `tfplugingen-framework` keys
  its generated Go helper types only by attribute name, not by full tree
  path, which produced two independent, unfixable collisions:
  `conflicting_access_criteria.{left_criteria,right_criteria}.criteria_list`
  (both branches reuse the identical leaf name `criteria_list`), and the
  top-level `owner_ref` vs. `violation_owner_assignment_config.owner_ref`
  (same name at different depths). This is the same failure class as
  `identitynow_segment_v1`'s `visibility_criteria` collision. Both fields
  were therefore `schema.ignores`'d in `generator_config_sod_policy_v1.yml`
  and hand-written/hand-converted directly, preserving the exact attribute
  names from the spec. A second, independent reason
  `violation_owner_assignment_config` was excluded from codegen/type-mapping
  is that its `assignment_rule` and nested `owner_ref.type` fields are
  `NullableString` in the SDK, a shape `tfplugingen-framework`'s generated
  To/From converter templates cannot handle.
- **Update is a full-replace `PUT`, not a `JSON-Patch`.** Unlike
  `identitynow_segment_v1`/`identitynow_governance_group_v1`, the
  `/sod-policies/v1/{id}` API exposes a real, working `PUT` endpoint, so
  Create and Update share the same request-body-building helper
  (`sodPolicyModelToDTO`) rather than needing hand-built JSON-Patch
  operations.
- **`policy_query` is API-computed for `CONFLICTING_ACCESS_BASED`
  policies.** The API derives `policy_query` itself from
  `conflicting_access_criteria` for that policy type; the field is left
  `Optional`+`Computed` in the generated schema (the spec has no `readOnly`
  marker on it), but practitioners managing a `CONFLICTING_ACCESS_BASED`
  policy should leave `policy_query` unconfigured and let the API populate
  it, rather than fight a perpetual diff.
- **`schedule` (`GET`/`PUT /sod-policies/v1/{id}/schedule`) and the
  evaluate/violation-report/violation-report-status endpoints are
  intentionally out of scope** for this CRUD resource - they model an
  asynchronous, request/status-poll workflow rather than declarative
  create/read/update/delete state, and are better suited to a
  purpose-built future resource/data source (or provisioning outside
  Terraform) than being force-fit into this one. No sub-resource for them
  exists yet in this provider.
- **Cross-reference**: the read-only
  [`identitynow_governance_group_connections_v1` data source](../data-sources/governance_group_connections_v1.md)
  surfaces a `SOD_POLICY` connection type for governance groups referenced
  as a policy or violation owner - see that data source's docs for the
  reverse-lookup relationship (a governance group's connections list will
  include an entry per SOD policy that references it as `owner_ref` or as
  `violation_owner_assignment_config.owner_ref`).
- **Practical requiredness of `name`/`owner_ref` is not yet live-confirmed.**
  The OpenAPI spec has no `required` array for either field, so both remain
  `Optional`+`Computed` in the generated schema, but every example in
  SailPoint's own documentation always populates both. Until Phase B (live
  sandbox) testing confirms otherwise, treat them as practically required
  even though Terraform will not enforce that for you.
- **Live sandbox-tenant verification is still pending for this pilot** as of
  its initial implementation - the schema/hand-written CRUD/build were
  validated offline (`go build`/`vet`/`test`, `golangci-lint`,
  `tfplugindocs`, `terraform validate`), but no `terraform plan`/`apply` has
  yet been run against a real tenant. Treat this resource with the same
  caution as any other freshly-added `_v1` pilot until that follow-up is
  completed.
