# identitynow_segment_v1 (Resource)

Manages a [Segment](https://developer.sailpoint.com/docs/api/v2025/create-segment) in IdentityNow/ISC.

~> This is a `_v1` pilot resource. `visibility_criteria` is hand-written here because the generated pipeline cannot represent the spec's repeated nested `value` blocks without a Go symbol collision; see the package doc for details.

## Example Usage

```terraform
resource "identitynow_segment_v1" "example" {
  name        = "example-segment"
  description = "Managed by Terraform."
  active      = true

  visibility_criteria = {
    expression = {
      operator = "AND"
      children = [
        {
          operator  = "EQUALS"
          attribute = "location"
          value = {
            type  = "STRING"
            value = "Philadelphia"
          }
        },
        {
          operator  = "EQUALS"
          attribute = "department"
          value = {
            type  = "STRING"
            value = "HR"
          }
        }
      ]
    }
  }
}
```

## Known Limitations & Live Testing Notes

This resource's schema/model types are generated by `tfplugingen-framework`
from SailPoint's per-service `/segments/v1` OpenAPI spec (service folder
`segments`); Create/Read/Update/Delete are hand-written against
`golang-sdk/v3`'s `segments.SegmentsAPIService` client.

- **`visibility_criteria` is entirely hand-written, not generated.** The
  spec's `visibilityCriteria.expression` tree has a "value" nested block
  that recurs at two different depths (`expression.value` and
  `expression.children.value`, both structurally identical) -
  `tfplugingen-framework` keys its generated Go helper types only by
  attribute name, not by full path, so this collided into an unfixable
  "ValueType redeclared in this block" build error. The entire
  `visibility_criteria` schema and its SDK conversions were therefore
  hand-written directly in `resource_segment.go`/`segment_data_source.go`/
  `segments_data_source.go`, preserving the exact attribute names/shape from
  the spec (matching the reference `davidsonjon/identitynow` provider's
  docs) rather than renaming anything to dodge the collision.
- **`visibility_criteria` is capped at exactly two levels**, matching the
  real API: `visibility_criteria.expression.children` exists, but each
  child's own `children` field is always `null` on the wire (the API's own
  spec comment reads "There cannot be anymore nested children. This will
  always be null.") and is intentionally omitted from this resource's
  Terraform schema entirely, rather than exposed as an always-null
  attribute.
- **`owner` is `Optional`, not `Required`** - live sandbox data shows many
  real-world segments have a `null` owner (e.g. segments created before
  ownership was enforced, or created via the UI without an owner).
- **Update only patches the fields the API's own PATCH doc lists as
  patchable**: `name`, `description`, `owner`, `visibility_criteria`,
  `active` - each is only included in the JSON-Patch request body when it
  actually changed between plan and prior state, following this provider's
  established conditional-patch idiom (see `sources_v1`/`role_v1`).
- **Live sandbox-tenant verification (Phase B) is complete for this
  resource.** A full create/plan(no-drift)/update (including a nested
  `visibility_criteria` leaf value)/import/destroy cycle was run against a
  real sandbox tenant, alongside `TF_ACC=1` acceptance tests.
