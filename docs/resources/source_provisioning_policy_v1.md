# identitynow_source_provisioning_policy_v1 (Resource)

Manages a [Provisioning Policy](https://developer.sailpoint.com/docs/extensibility/transforms/guides/transforms-in-provisioning-policies) on an existing [Source](https://documentation.sailpoint.com/saas/help/sources/index.html) in IdentityNow/ISC. A provisioning policy is a create/update/enable/disable/etc. template (keyed by `usage_type`) used when provisioning accounts on the source.

~> This is a `_v1` pilot resource - see "Known Limitations & Live Testing Notes" below before relying on it in production configurations. In particular, it uses SailPoint's v1 provisioning-policies API (keyed by `source_id`+`usage_type`), not the newer v2 by-id API, because the published golang-sdk has no v2 bindings yet - see this package's doc comment for the full rationale.

## Example Usage

```terraform
# A Provisioning Policy defines which fields are requested/set for a given
# usage type (e.g. CREATE, UPDATE, ENABLE, DISABLE) when IdentityNow
# provisions to this source. usage_type + source_id together form this
# resource's identity - the API has no separate real "id" of its own (see
# "Known Limitations & Live Testing Notes" for why this uses v1, not v2,
# endpoints).
resource "identitynow_source_provisioning_policy_v1" "example" {
  source_id   = "9e99be10dcf24aa9bbe83902dece8738"
  usage_type  = "CREATE"
  name        = "Create Account"
  description = "Managed by Terraform."

  # "fields" is connector/usage-type-specific and can itself nest a full
  # transform definition per field - modeled as a raw JSON string (see this
  # resource's "Known Limitations & Live Testing Notes" documentation
  # section for the full rationale, matching identitynow_transform_v1's
  # "attributes" and identitynow_source_v1's "connector_attributes").
  fields = jsonencode([
    {
      name          = "userName"
      transform     = { type = "accountAttribute", attributes = { attributeName = "userName", sourceName = "Employees" } }
      attributes    = {}
      isRequired    = true
      type          = "string"
      isMultiValued = false
    },
  ])
}
```

## Schema

### Required

- `name` (String) the provisioning policy name
- `source_id` (String) The Source ID.
- `usage_type` (String) The type of provisioning policy usage. 
In IdentityNow, a source can support various provisioning operations. For example, when a joiner is added to a source, this may trigger both CREATE and UPDATE provisioning operations.  Each usage type is considered a provisioning policy.  A source can have any number of these provisioning policies defined. 
These are the common usage types: 
CREATE - This usage type relates to 'Create Account Profile', the provisioning template for the account to be created. For example, this would be used for a joiner on a source.  
UPDATE - This usage type relates to 'Update Account Profile', the provisioning template for the 'Update' connector operations. For example, this would be used for an attribute sync on a source.
ENABLE - This usage type relates to 'Enable Account Profile', the provisioning template for the account to be enabled. For example, this could be used for a joiner on a source once the joiner's account is created. 
DISABLE - This usage type relates to 'Disable Account Profile', the provisioning template for the account to be disabled. For example, this could be used when a leaver is removed temporarily from a source.
CREATE_MACHINE_ACCOUNT - This usage type can be used to create the provisioning template for a source subtype which will be used in creating a machine account.
You can use these usage types for all your provisioning policy needs.

### Optional

- `description` (String) the description of the provisioning policy
- `fields` (String) The list of fields (attribute-to-transform mappings) that make up this provisioning policy's template, as a raw JSON array. Each element's shape matches the API's FieldDetailsDto - see https://developer.sailpoint.com/docs/extensibility/transforms/guides/transforms-in-provisioning-policies for examples. This is a raw JSON string (via jsontypes.Normalized, semantic not textual equality) because each field's own "transform"/"attributes" sub-properties are a discriminated union keyed by a sibling "type" - the same shape as identitynow_transform_v1's "attributes" attribute.

### Read-Only

- `id` (String) Synthesized composite id in the form `source_id/usage_type` (`ProvisioningPolicyDto` has no native id).

## Known Limitations & Live Testing Notes

This resource is a `_v1` pilot. `identitynow_source_v1`'s own docs note
provisioning policies and schemas as sub-resources of a Source deferred to
"a future, separate resource/data source" - this is that resource for
Provisioning Policies (see `identitynow_source_schema_v1` for Schemas).

- **v1, not v2, endpoints were deliberately used**, despite a newer
  `/sources/v2/{sourceId}/provisioning-policies/{id}` API existing with a
  cleaner real-`id`-keyed CRUD shape (POST/GET/PUT/DELETE all by `id`,
  rather than v1's composite `sourceId` + `usageType` key plus a
  bulk-update-only PATCH). The vendored `golang-sdk` (confirmed through
  `v2.7.106`) implements **zero** v2 provisioning-policy bindings at all -
  only v1's `CreateProvisioningPolicy`/`GetProvisioningPolicy`/
  `UpdateProvisioningPolicy`/`PutProvisioningPolicy`/
  `DeleteProvisioningPolicy`/`ListProvisioningPolicies`. v2 additionally
  requires a mandatory `X-SailPoint-Experimental` request header that the
  SDK has no way to attach. This is a deliberate deviation driven entirely
  by an SDK gap, not a spec-quality judgment - if/when the SDK adds v2
  bindings, revisiting this resource to move to `id`-keyed v2 CRUD (a
  strictly better fit for Terraform's resource model) would be worth
  doing.
- **This resource's Terraform `id` is a synthesized composite**
  (`<source_id>/<usage_type>`), not a real API-issued id -
  `ProvisioningPolicyDto` has no native `id` field of its own. Changing
  either `source_id` or `usage_type` forces replacement (they identify an
  entirely different policy).
- **`usage_type`** identifies which provisioning use case this policy
  configures - e.g. `CREATE`, `UPDATE`, `ENABLE`, `DISABLE`. A source can
  have at most one provisioning policy per usage type.
- **`fields` is modeled as a raw JSON string** (`jsontypes.Normalized` -
  semantic, not textual, equality), not a fixed Terraform schema. Each
  array element (`FieldDetailsDto`) has its own `transform` sub-object,
  itself a discriminated union keyed by a sibling `type` whose shape can
  recursively nest another full transform definition - identical in kind
  to `identitynow_transform_v1`'s top-level `attributes` field and
  `identitynow_source_v1`'s `connector_attributes`. See those resources'
  own "Known Limitations" sections for the general rationale behind this
  pattern.
- **Update uses `PATCH` (RFC 6902 JSON Patch)**, matching
  `identitynow_source_v1`/`identitynow_role_v1`/
  `identitynow_service_desk_integration_v1`'s existing JSON-Patch
  update-helper pattern, not the also-available full-replace `PUT` variant.
- **A plural `identitynow_source_provisioning_policies_v1` data source is
  fully hand-written**, not generated by `tfplugingen-framework` (which has
  no "list" operation concept) - it reuses this resource's own generated
  schema/model types, mirroring `identitynow_roles_v1`'s precedent.
- **Phase B (live `terraform plan`/`apply` against a real sandbox tenant)
  is pending.** This pilot was built in a worktree without sandbox
  credentials (`test/.env`) - Phase A (build/vet/lint/docs/examples/tflint)
  passed, but no live create/read/update/delete has yet been exercised
  against a real IdentityNow/ISC tenant. In particular, watch for: whether
  `fields` round-trips byte-for-byte through `jsontypes.Normalized`'s
  semantic comparison once populated with a real connector's field
  definitions, and whether any Computed-only attribute needs a
  `UseStateForUnknown` plan modifier beyond what's already applied here
  (see `resource_source_provisioning_policy_planmodifiers.go`).
